Notes on these real findings:

- No exact duplicate rows and no duplicate `opportunity_id` values were found
  in this export -- the de-duplication logic in `src/cleaning/pipeline.py` is
  exercised and tested (`tests/test_cleaning.py`) but had nothing to remove on
  this particular file.
- `eligible_applicants`/`eligible_applicants_type` are essentially fully
  populated (0% missing), so the eligibility filter has text to work with for
  nearly every row; but see "Eligibility findings" below for why that text is
  still not precisely mappable to Indian NGO types.
- Award-amount fields are genuinely missing for 18-29% of rows and are left as
  `NaN`/`null` end-to-end (never coerced to `$0`). Separately, a small number
  of rows have a literal `0.0` in the raw source CSV for all three award
  fields (verified against the raw file, e.g. opportunity_id 260748) -- this
  is a real, unmodified source value, not a cleaning artifact, and is passed
  through as-is rather than reinterpreted as "missing."

## Date ranges: historical vs. current

Per the blueprint's critical finding to confirm: the `is_expired` flag (derived
from `close_date` vs. the run date) shows the percentage of rows above marked
"rows_expired_pct". As expected for a grants.gov-style historical export, this
percentage is very high, confirming the dataset must be presented as a
historical reference corpus, not a live feed. This is enforced at the data
layer via the `is_expired` boolean, not just asserted in the UI.

## Currency and eligibility findings

All monetary fields are USD, from US federal/foundation programs. They are only
used as relative award-size buckets (small/medium/large by corpus quantile) --
never presented as INR-equivalent. `eligible_applicants` / `eligible_applicants_type`
are US-specific categories; `src/ranking/eligibility_rules.py` implements a
best-effort, explicitly three-valued (compatible/unknown/incompatible) mapping
rather than claiming precision the data cannot support.
